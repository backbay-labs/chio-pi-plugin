# Chio Pi: research and product ideas

Research date: October 4, 2026. Local source examined: `b24b14e` on
`codex/pi-kernel-integration`. This is a research memo, not implementation or
release qualification. Proposed names below illustrate interfaces; they are not
existing commands or APIs.

## Recommendation

Turn the existing execution boundary into a capable development workflow with
understandable approval, recovery, and evidence. The adapter's execution machinery
is substantially ahead of its everyday usefulness. A useful product should let a
developer fix and test a change, review the exact deliverable, authorize its
publication, and recover the original outcome after an interruption.

The near-term choices with the strongest case are:

1. Typed native Pi tools backed by the existing executor.
2. An operator console for scope, approvals, and original-outcome recovery.
3. A constrained coding workspace with search, diffs, and resource-owned test jobs.
4. A separately qualified Pi 1.0.2 compatibility lane.

The larger opportunities are a Chio execution adapter for Pi Durable, policy-aware
model context and artifacts, and continuity across hosts. Their product value is
a hypothesis requiring comparison and independent use.

Confidence is high in the source observations and local test results, moderate in
the implementation recommendations, and unknown in adoption and willingness to
pay. No demand interviews or new live-kernel acceptance were performed here.

## What exists today

The checked-in package is `@chio/pi-plugin@0.1.0` and pins Pi 0.85.1. The installed
`chio-pi` launcher owns the model relay, Chio transport, and private operation
journal. The guest is confined with macOS Seatbelt, receives ephemeral local
transport credentials, and cannot directly reach the kernel. Pi exposes one
native tool, `chio_execute`. The kernel resource owner executes protected work.

`src/extension.ts` accepts a string tool name and an open argument record.
`src/session.ts` puts the complete configured inventory into the system prompt,
disables resource discovery, and uses a native SDK tool allowlist. It also selects
sequential execution. `src/http-executor.ts` verifies exact request, receipt, and
result bindings. `src/protected-cli.ts` acknowledges completed outcomes after the
relay observes their full representation in Pi's native tool history.

The currently promised workflow is kernel-owned read, write, edit, and directory
listing. Interactive commands, arbitrary MCP servers, delegation, attachments,
native shell development, and background jobs are excluded. The launcher accepts
only `openai/gpt-4.1-mini` or `openai-codex/gpt-5.5` and emits JSONL.

The final qualification record is more current than the historical acceptance
table. For frozen source `2ccc027b...` and archive `ec609539...`, it records actual
approvals, expiry, aggregate budget crossing, revocation, result substitution,
storage failures, interruption, and original-outcome recovery. The compatible
public release remains open. API-billing evidence belongs to earlier archives.
The hung-extension case uses the qualification driver's watchdog, rather than a
production launcher deadline.

The frozen fault-recovery path also requires a separately pinned operator utility
and resource-owner exporter. Its recovery procedure is correct in retaining the
original operation, but it takes several operator steps and crosses artifact
boundaries that should become easier to understand.

I reran `npm run typecheck` and `npm test` on the inspected checkout. Typecheck,
build, and all 23 component tests passed, with no skipped tests. Those tests use
stock Pi with scripted providers or component seams. Their success does not
requalify the frozen real-kernel combination at the current commit.

## What changed upstream

Pi 1.0 shipped on October 1. Its release introduced native MCP, codemode, deferred
tools, and additional extension features. The latest registry version inspected
on October 4 is 1.0.2. Pi Durable shipped alongside 1.0 as a separate experimental
package. [Pi 1.0 announcement](https://earendil.com/posts/pi-1-0/),
[current changelog](https://pi.dev/changelog).

Current extension contracts distinguish tools declared to the model from tools
callable by another tool. They expose nested execution, tool namespaces,
structured output, and unverified effect annotations. These can improve Chio's
interface, but annotations do not establish permission or recovery safety.
[Extension contracts](https://pi.dev/docs/latest/extensions).

Codemode executes JavaScript in QuickJS with no direct Node, filesystem, network,
or timer APIs. It reaches external resources through registered tools and model
services. Tool calls that complete before a script failure remain real effects.
This creates an attractive orchestration surface and a new delivery/recovery
problem. [Codemode contract](https://pi.dev/docs/latest/codemode).

Pi's official isolation guide includes whole-process containers and sandboxes,
credential proxies, OpenShell, and a Gondolin tool backend. Isolation and keeping
provider credentials outside the guest already have alternatives in this
ecosystem. Chio needs to demonstrate additional value through scoped authority,
recoverable effects, policy-aware disclosure, and evidence.
[Isolation guide](https://pi.dev/docs/latest/containerization),
[security boundary](https://pi.dev/docs/latest/security).

Pi Durable checkpoints tasks and supports tool recovery. Its current tool task
implementation reruns only when both the retained and current tool policies say
`safe`; otherwise it reports interruption. A submission request ID deduplicates
submission intake. Neither observation alone establishes the outcome of an
external effect. Chio could supply that missing resource-specific reconciliation.
[Durable announcement](https://earendil.com/posts/pi-durable/),
[v1.0.2 tool task](https://github.com/earendil-works/pi/blob/v1.0.2/packages/durable/src/harness/tool.ts).

I downloaded both 1.0.2 npm archives with lifecycle scripts disabled and inspected
their published implementations and declarations in a temporary directory. The
coding-agent SDK still filters extension tools through its explicit allowlist.
The new declared/callable distinction is an audit requirement for future changes,
not a demonstrated bypass of the current Chio profile. Version 1.0.1 also removed
Pi's published npm shrinkwrap, so a Pi peer version alone no longer freezes its
transitive installation graph. A future Chio lane must retain the exact consumer
dependency graph it qualifies. [Changelog](https://pi.dev/changelog).

### 1. Typed native tools

Generate a small set of Pi tool definitions from the operator-pinned inventory.
Illustrative names are `chio_read`, `chio_edit`, `chio_list`, and `chio_write`.
Each definition carries the actual input schema and maps to one configured kernel
tool through the existing executor. The gateway still binds caller, tool,
arguments, request ID, and result. Schema validation provides useful feedback;
the kernel remains responsible for permission and effects.

Start with the existing four tools. Larger inventories could use namespaces and
deferred discovery after the upgraded host is qualified. Dynamic activation must
be bounded by the operator's registry snapshot, with a schema digest included in
the session compatibility identity.

The relay currently recognizes only `chio_execute` in declarations, choices, and
history. Typed tools therefore require coordinated relay validation and outcome
parsing changes. Tool rendering can hide receipt details from the human's primary
view while native history retains the exact representation required by ACK. A
separate signed compact delivery projection would require a new verified
contract; silently trimming the existing outcome would break the boundary.

Experiment: compare the generic wrapper and typed definitions on identical tasks,
model settings, resource state, and policy. Measure malformed arguments, wrong
tool selection, task success, turns, context size, and result-delivery correctness.
Keep the change if it improves usability with unchanged effect ownership and
recovery behavior.

### 2. An operator console for approval and recovery

Build an operator surface that displays the current resource scope, allowed
tools, authority expiry, remaining invocation budget, pending proposals, and
operation state. Illustrative controls are status, inspect request, approve exact
proposal, reject, reconcile original outcome, and resume.

The display should distinguish no dispatch, pending approval, dispatched with
unknown outcome, verified completion awaiting delivery, and acknowledged
completion. A completed model answer must not replace those states. The console
should retrieve authoritative gateway/kernel state and present an appropriately
scoped view rather than infer truth from Pi's mutable session file.

Use the native SDK's event and session contracts for conversation presentation.
Keep operator grants in the trusted parent or operator process, authenticated
separately from the guest. The current launcher's ignored stdin and print-only
execution mean a full interactive TUI is a real host-surface change. A trusted
status/recovery CLI is the smaller first step. Wrap the pinned bridge operator
procedures coherently, preserving their custody and verification checks.

Experiment: have another developer recover a response-loss case using only the
console and published instructions. Measure steps, time, mistakes, and recovery
to the exact original operation. Recovery without trustworthy completed evidence
must remain explicitly unresolved.

### 3. A useful constrained coding workspace

Add resource-owned search, file-range reads, repository status, diff generation,
patch application, and bounded test jobs. The Pi process stays confined; source
and test execution live in the designated resource environment.

A test tool should select an operator-defined recipe, environment image, working
directory, and resource limits. Repository tests still execute arbitrary code,
including package hooks and subprocesses. The resource environment therefore
needs its own filesystem, descendant, network, credential, and persistence
boundary. A recipe is not a sufficient security boundary by itself.

Initially keep credentials and publication authority out of that environment.
Treat network access and package installation as separately scoped operations.
Patch application can bind an expected base digest and reject stale source.
Test results should name the exact source and recipe digests. A separate
publication participant can require approval of the exact tested artifact.

Experiment: reproduce and fix a real small bug in a disposable repository copy,
run the relevant test, inspect the diff, and publish the reviewed patch to its
designated owner. Kill the launcher after publication and recover the original
artifact without a replacement dispatch. Add GitHub publication only after its
provider lookup and ambiguous-outcome contract is qualified.

### 4. A Pi 1.0.2 compatibility lane

Keep the frozen Pi 0.85.1 evidence intact and create a separate candidate for
1.0.2. Recheck registry filtering, deferred and nested tools, native MCP startup,
model history, compaction, branch replacement, provider routing, and cold install.
Include the host's complete transitive dependency graph in the candidate
identity, given the upstream shrinkwrap change.

Re-run the existing component suites first, then the real installed-host matrix.
New host features should enter the supported action inventory only when their
useful behavior, effect paths, cancellation, result delivery, and recovery are
observed. This research did not install the new host into the project or run a
new-host acceptance matrix.

### 5. Repository context without executable discovery

The current profile deliberately disables AGENTS files, skills, prompt templates,
and project extension discovery. Introduce an operator-selected context package
retrieved through the resource boundary: repository identity, revision, selected
project instructions, useful structure, and allowed test recipes.

Bind the contents to source digests, size limits, and any disclosure labels.
Project instructions provide context and cannot grant authority. Treat skill text
as task guidance; any requested action still goes through a configured kernel
tool. Preserve the context identity in checkpoints and compaction metadata so
resume detects incompatible inputs.

Experiment: compare task success and startup read calls with and without the
context package. Add malicious project instructions and confirm that useful work
continues without loading code or widening authority.

### 6. Explain blocked actions and offer lawful continuations

Expose a scoped read-only explanation tool that answers why an operation is
blocked and which supported next actions could satisfy its requirements. A
pending proposal can resume through its native exact-request path. A frozen
denial needs a new linked continuation if policy permits one. An unknown effect
requires reconciliation of the original operation.

The live recovery worktree's README now records P2 explanations, P3 semantic
remedies, and P4 labeled artifacts as locally implemented for bounded profiles.
P5 still requires real Linux cage acceptance. These are separate implementation
records, not APIs qualified in this plugin's bundled bridge or frozen kernel.
Use their operating contracts to design a bridge compatibility crosswalk.

The adapter can render alternatives such as exact approval, authorized
transformation, alternate destination, prerequisite, and withholding. Offers are
advisory. Execution must revalidate the applicable current authority and evidence.
Hidden policy facts must not leak through alternative names or ranking.

Experiment: one denied task progresses through an authorized remedy, retains its
source restrictions, and produces one verified permitted effect. Changed approval
arguments, stale explanations, and forged offers must fail.

### 7. A Chio execution adapter for Pi Durable

Let Pi Durable manage conversations, checkpoints, queues, and application state.
Let Chio manage protected authority and external operation truth. Implement a
native durable tool that calls the existing execution boundary and retains an
immutable mapping from conversation/task/call identity to the Chio operation.

On recovery, the tool must consult the original operation before dispatch.
Verified completed work returns the original result. Pending approval preserves
its proposal. Unknown work remains fenced. Authoritative evidence that nothing
was dispatched can permit the appropriate continuation. A host replay annotation
alone cannot make these distinctions.

Begin with `unsafe` replay and an explicit recovery path. Consider replaying a
recover-or-execute wrapper only after every cutpoint proves that it reuses the
original identity, preserves live authority checks, and cannot produce a second
effect. Keep this as a distinct host acceptance lane, since Pi Durable's API is
experimental and differs from the coding-agent SDK.

Experiment: use a filesystem participant first, then a provider with qualified
operation lookup. Compare ordinary Pi Durable and Chio-backed Durable for crash
recovery, operator effort, duplicated effects, budget accounting, and complexity.

### 8. Govern model context and artifact reuse

The current relay fixes the provider and hides credentials, but it forwards
permitted inline text. That alone does not implement confidentiality or purpose
rules for resource content sent to the model.

A future trusted relay can consume kernel-verified disclosure records binding
content, classification, recipient/provider, account, model, purpose, and relevant
policy. It can select an authorized projection before bytes leave for a provider.
Labels and lineage need to survive summaries, checkpoints, derived artifacts,
and host changes. User input also needs an explicit ingress policy. Mutable guest
metadata and probabilistic secret detection cannot grant disclosure rights.

This is potentially a stronger enterprise reason to adopt Chio than another
credential proxy. Its usefulness depends on the compatible P3-P5 kernel profile,
complete channel coverage, conservative derivation rules, and usable denial UX.

Experiment: a labeled private source yields an authorized public projection.
Exercise resume, summary, cache, and alternate-model paths. Observe the actual
provider request and confirm that excluded content never crosses the boundary.

### 9. Continue work across Pi and another host

Provide a governed handoff package containing the authoritative workflow reference,
artifact identities, required evidence, approvals, and unresolved operations.
The receiving host validates provenance and receives explicitly scoped authority.
Conversation export is useful context but cannot serve as a recovery grant.

This lets a Pi session hand work to another Chio integration without erasing
uncertainty or treating a new conversation as a new permission to act. Scope,
labels, quota accounting, and historical settlement must survive the transfer.
Use shared bridge/kernel contracts so each adapter does not invent a parallel
handoff protocol.

Experiment: interrupt Pi after a protected effect and resume the workflow through
one other real host. Prove recovery of the original outcome, retained restrictions,
and independent observation of zero replacement effects.

### 10. Bounded delegation

Support a launcher-owned child factory with separate profiles and explicitly
attenuated capabilities. Example roles are a read-only scout, a patch-producing
worker, and a reviewer. Code-writing and publication rights can be separate.

Children need an authority, budget, cancellation, and unresolved-operation model
that remains valid after the parent dies. Their results should bind the child
identity and exact artifact provenance. The guest must not spawn arbitrary Pi
processes or load user-defined executable agent packages.

Experiment: one read-only child and one patch child complete useful work, while
attempted authority widening and publication fail. Parent cancellation and crash
must retain child operation truth. Validate parent/child quota accounting before
promising a fleet feature.

### 11. Governed codemode and compound operations

Codemode could reduce model turns for read-heavy work by filtering data close to
the tool calls. The current transport intentionally fences a second operation
until the first result appears in native model history. Sequential execution
alone does not solve that delivery requirement.

Explore either independently verified nested-call delivery or one kernel-owned
compound operation with child identities and bounded execution. Do not ACK an
effect merely because a script promises to include it in its final text. A
script can filter, throw, be cancelled, or end after partial effects. Unprinted
results still need authoritative retention and reconciliation.

Start with bounded read aggregation. Require per-child records and explicit
partial completion before allowing mixed-effect plans. Avoid claiming atomic
rollback of unrelated external systems.

Experiment: inject a failure after the first child result and before script
output. Recover every completed/unknown child truthfully with no hidden retry.
Measure model turns, bytes, tokens, and added journal work on a fixed workload.

### 12. Operational limits and portable confinement

Add parent-enforced wall-clock deadlines, provider request limits, conservative
token reservations, and explicit tool timeouts. The launcher must stop hung work
without interpreting termination as proof that an effect did not happen. Retain
unresolved original operations and reserve uncertain usage conservatively.
Invocation budgets enforced by the kernel and model consumption limits are
different counters. Subscription dollar estimates should remain advisory.

Represent supported provider/model combinations as versioned, operator-selected
transport profiles. Each profile needs route, request, history, credentials, and
ACK conformance. Model switching cannot be a model-selected fallback around a
refusal or data-disclosure restriction.

Linux support could use a whole-process confinement backend with equivalent
filesystem, credential, descendant, and network guarantees. The launcher should
test the selected backend before accepting protected work. Preserve the same
resource-owned execution path across operating systems.

Experiment: deadline an intentionally hung extension and a post-dispatch call;
observe correct terminal states and recovery. For each new confinement backend,
run both useful-work controls and hostile file/process/network probes against
the exact launched policy.

## First implementation sequence

1. Make current status readable. Route the README and acceptance page to the
   final frozen record, clearly separate current-head component results, and
   expose a trusted read-only doctor/status command. The historical release
   setup notes should be refreshed before treating them as current blockers.
2. Qualify Pi 1.0.2 as a separate lane with exact dependency identities. Initially
   retain the existing four-tool surface and all delivery constraints.
3. Add typed tools and operator-visible scope/operation state. Compare the wrapper
   on useful tasks rather than assume a token or success improvement.
4. Deliver one coding workspace slice with governed context, search, patch,
   constrained tests, diff review, and exact artifact publication.
5. Integrate scoped explanation/recovery from a compatible kernel build. Package
   operator recovery coherently while preserving its separate trust boundary.
6. Choose one expansion experiment: Pi Durable for long-running applications, or
   cross-host continuation for the existing integration program. Decide using
   actual consumer tasks and adoption evidence.

The first product acceptance should be a developer fixing a real bug through the
protected mode, publishing an approved tested artifact, experiencing an injected
post-effect interruption, and recovering its original outcome using understandable
operator controls. Include an attempted forbidden action and continued legitimate
work under the same original authority.

## What would change the recommendation

Measure useful-task completion, false refusals, setup steps, time to first useful
result, model turns/tokens, tool intervals, manual interventions, and recovery
correctness. Keep ordinary no-fault behavior and failure behavior separate.
Use independent resource observation for effect counts and authoritative records
for request identity and budgets.

Compare a standard isolated Pi workflow, the current Chio wrapper, and the
proposed Chio workflow on the same tasks. Security capabilities differ, so report
those differences instead of calling unlike boundaries equivalent. For the
Durable experiment, compare both harness recovery and external-effect recovery.

The existing three-pair latency observation is too small and noisy to select a
performance strategy. It records paired differences of 2,450.881 ms, -215.677 ms,
and 264.299 ms. Preserve its measurement scope. Collect more instrumented samples
before identifying a bottleneck, removing persistence, or promising percentiles.

Stop expanding a candidate if it only adds a new UI label, duplicates host
durability without improving protected-effect outcomes, widens guest authority,
cannot recover partial execution, or makes useful development materially harder
without demonstrating the required protection. Advance when an independent user
can complete and recover the chosen workflow with less application-specific code
and fewer operator mistakes.
